# SCSS のルール（FLOCSS・社内共通／叩き台）

> **叩き台です。** 【論点n】と書いた所は、チームで決める前の仮の決まりです（チームの提案書を参照）。
> 案件だけの値と決定は、ここに書かず、案件の `CLAUDE.md` と SCSS の `global/` に書きます。

共通のルール（アクセシビリティ・クラス名の役割分担）は `CLAUDE.md` を参照。

## 1. ファイル構成（FLOCSS）

```
scss/
├── style.scss        … 各 index を @use するだけ
├── global/           … CSS を出力しないもの（変数・関数・mixin）
│   ├── _index.scss     … @forward でまとめる
│   ├── _variables.scss … Sass 変数（ブレークポイントなど）
│   ├── _function.scss  … 関数
│   └── _mixin.scss     … mixin
├── foundation/       … リセット・ベース・:root の CSS 変数
│   ├── _reset.scss
│   ├── _root.scss      … デザイントークン（CSS カスタムプロパティ）
│   └── _base.scss
├── layout/           … ページの骨組み（接頭辞 l-）
└── object/
    ├── component/    … 再利用する小さな部品（接頭辞 c-）
    ├── project/      … ページ・機能ごとのまとまり（接頭辞 p-）
    └── utility/      … 微調整用（接頭辞 u-）
```

（【論点6】`global/` を分けること、utility を `object/` の中に置くこと）

- 1つの部品につき1ファイル。ファイル名は、クラス名から接頭辞を取ったもの（`.c-news-list` → `_news-list.scss`）。
- 新しいファイルを作ったら、同じ階層の `_index.scss` に `@forward` を足す。
- **`global/` には、CSS を出力する記述を書かない。** 部品のファイルが mixin を使うために読み込む場所なので、
  ここに CSS があると、エディタ用の CSS など、別の出力ファイルにも同じ CSS が入ってしまう。
- 各ファイルの先頭は `@use "../global/index" as g;`（階層に合わせる）。共通のものは `g.` を付けて呼ぶ。
- `@import` は使わない（Sass で廃止が決まっている）。`@use` / `@forward` を使う。
- コンパイルは、案件の `CLAUDE.md` に書いた方法で行う（【論点5】npm の `sass` を標準にする）。
  出力された `.css` は、直接編集しない。

## 2. 層ごとの役割

| 層 | 書くもの | 書かないもの |
|---|---|---|
| layout（`l-`） | ヘッダー・フッター・コンテンツの幅と左右の余白など、ページの骨組み | 中に入る部品の見た目。`c-` `p-` のクラスへの指定 |
| component（`c-`） | どのページでも使える部品（ボタン・見出し・カード） | 置かれる場所で変わる余白（外側の `margin`）。ページ名の入った指定 |
| project（`p-`） | そのページ・機能だけのまとまり。部品の並べ方と、部品の間の余白 | ほかのページで使い回す前提の部品（使い回すなら `c-` に移す） |
| utility（`u-`） | 1つの役目だけの微調整（`u-text-center` など） | 複数のプロパティを組み合わせた見た目 |

- **ほかの層・ほかの部品のクラスを、自分のファイルの中で上書きしない。**
  変えたいときは、その部品にモディファイアを足すか、置く側（`p-`）で自分のクラスを付ける。

## 3. 命名

- BEM に、FLOCSS の接頭辞を付ける：`.c-news-list` / `.c-news-list__item` / `.c-news-list__item--new`
- 単語は、小文字とハイフンでつなぐ（`l-menuBtn` のようなキャメルケースを使わない）。省略しない（`c-btn` ではなく `c-button`）。【論点7】
- 中の部品は `__`、種類ちがいは `--`。中の部品を `--` で書かない。
- **モディファイアは、つなげた形（`block__element--modifier`）で書く**（2026-11-11 決定）。独立させた形（`.--wide`）は使わない。
  HTML では、元のクラスと並べて書く：`class="l-container l-container--wide"`
- エレメントを2段につなげない（`c-card__body__title` ではなく `c-card__title`）。
- 接頭辞の無いクラスを作らない。ページの中の部品にも `p-` を付ける（`about__title` ではなく `p-about__title`）。
  外部ライブラリ・WordPress が出力するクラスは例外。【論点7】
- モディファイアだけを単独で使わない（`class="c-heading--02"` ではなく `class="c-heading c-heading--02"`）。
- 状態は `is-` で始め（`isFixed` `open` `fixed` ではなく `is-fixed` `is-open`）、必ず BEM クラスと組み合わせて書く
  （`.c-accordion__panel.is-open`）。`is-` だけに CSS を書かない。【論点8】
- `js-` で始まるクラスには、CSS を書かない。【論点8】
- ネストで `&__element` と書くときは、**直前に完全なクラス名をコメントで書く**（エディタの検索で見つけられるように）。

```scss
.c-news-list {
  // .c-news-list__item
  &__item {
    // .c-news-list__item--new
    &--new { … }
  }
}
```

- ネストは、`&` を使ったもの（エレメント・モディファイア・状態・疑似クラス・メディアクエリ）だけ。
  子孫セレクタ（`.c-card .c-button`）でのネストはしない。

## 4. デザイントークン

- **色・文字サイズ・秒数・角丸・コンテンツ幅は、`foundation/_root.scss` の CSS 変数が正。**
- 色は必ず `var(--color-xxx)` で使う。16進数を、部品のファイルに直接書かない。【論点4】
- 色の変数は2段にする：元の色（`--color-blue`）と、役目の名前（`--color-main: var(--color-blue)`）。部品では、役目の名前を使う。
- 透明度を付けるときは `color-mix()` を使う（`color-mix(in srgb, var(--color-main) 30%, transparent)`）。
- **新しいトークンは、`_root.scss` に定義してから使う。** 定義の無い CSS 変数を使うと、エラーにならずに
  その指定だけが効かなくなる（気づきにくい）。
- そのファイルの中だけで使う変数は、`--_` で始める（`--_inner-width`）。
- Sass 変数（`$`）は、CSS 変数で表せないもの（ブレークポイントなど）だけに使う。
- デザインデータ（Figma の変数）・`theme.json` と、名前をそろえる。

## 5. 必ず使う関数・mixin

**生の `@media`・`clamp()`・`&:hover` を書かない。** `global/` に用意したものを使う。

| 用途 | 書き方 | 備考 |
|---|---|---|
| メディアクエリ（その幅以上） | `@include g.mq-up(md) { }` | 【論点2】 |
| メディアクエリ（その幅未満） | `@include g.mq-down(md) { }` | 【論点2】 |
| 画面幅で変わる値 | `g.fluid-clamp(16, 18)` | 単位なしの数値（px 相当）。最小幅〜基準幅の間でなめらかに変わる |
| px 相当の値を rem に | `g.px-to-rem(24)` | 文字サイズ・余白 |
| ホバー | `@include g.hover { }` | `:focus-visible` も同時に定義し、タッチ端末を除く |
| フォーム部品の文字 | `@include g.form-font-size;` | iOS の自動ズームを防ぐ（16px 以上） |
| 行間 | `@include g.line-height(18, 42);` | 文字サイズと行の高さ（px） |
| 字間 | `@include g.letter-spacing(50);` | 1000分率 |

- **狭い画面を基本にして書く**（モバイルファースト）：基本の指定がスマホ、`g.mq-up(md)` の中に広い画面の指定。【論点2】
  `g.mq-down()` は、「スマホのときだけ」の指定を、短く書けるときに限って使う。1つの案件の中で、基本の向きを混ぜない。
- ブレークポイントは `$mq-breakpoints` の名前で指定する（数値を直接書かない）。
  共通は `sm`（576）/ `md`（768）/ `lg`（1024）/ `xl`（1280）/ `menu-change`（メニューの形が変わる幅。案件で決める）。【論点12】
  端末の名前（`pc` `tablet` `sp`）や、数値の名前（`bp1430`）は付けない。
- `menu-change` は、JS の定数（`MEDIA_QUERIES`）と対になっている。**片方だけ変えない。**
- 可変の基準幅（`$min-viewport` / `$base-viewport`）は、案件の `global/` で決める。

## 6. プロパティの書き方

- レイアウトは Grid / Flexbox。`float` は使わない。要素の間は `gap` で空ける。
- **論理プロパティを使う。**【論点3】

| 物理（使わない） | 論理（使う） |
|---|---|
| `margin-top` / `-bottom` | `margin-block-start` / `-end` |
| `margin-left` / `-right` | `margin-inline-start` / `-end` |
| 上下 / 左右の `padding` | `padding-block` / `padding-inline` |
| `width` / `height` | `inline-size` / `block-size` |
| `top` / `left` | `inset-block-start` / `inset-inline-start` |

- **要素の間の余白は、上（`margin-block-start`）に付ける。** 上と下の両方に付けると、どちらが効いているかわからなくなる。
- 部品（`c-`）自身には、外側の余白を付けない。置く側（`p-`・`l-`）で付ける。
- `!important` を使ってよいのは、utility と、エディタ本文の枠の中で WordPress・プラグインの CSS を上書きするとき
  （理由をコメントに書く）だけ。【論点10】
- 広く当てるリセット・ベースは `:where()` で包む（あとから上書きしやすくなる）。
- `z-index` は、数値を直接書かず、`_root.scss` に並べた変数を使う（重なりの順番を1か所で見られる）。
- `transition: all` は使わない。変えるプロパティを書く。

## 7. 新しい CSS の機能を使うときの基準

「新しい書き方を使う。ただし、使えないブラウザがある機能で、表示を壊さない」ための基準。
Baseline（主要なブラウザすべてで使えるかを示す、共通の目安。MDN や Can I use に表示される）で決める。

| Baseline の表示 | 意味 | 使い方 |
|---|---|---|
| Widely available | 主要なブラウザすべてで使えるようになって、約2年半たった | **そのまま使う** |
| Newly available | 主要なブラウザすべてで使えるようになったばかり | 使えなくても表示が壊れない所（飾り・動きなど）なら使う。レイアウトに関わる所は、`@supports` で代わりの指定を用意する |
| Limited availability | まだ使えないブラウザがある | **使わない**（使えなくても何も困らない、純粋な飾りだけ例外） |

- 迷ったら、使う前に Baseline の表示を確かめる。確かめずに「たぶん使える」で書かない。
- 例（目安。使う前に確かめる）：
  - そのまま使えるもの：論理プロパティ、`gap`、`clamp()`、`:where()` `:is()`、`:focus-visible`、`aspect-ratio`、
    メディアクエリの範囲の書き方（`width < 768px`）、`color-mix()`、`inert`、`:has()`、コンテナクエリ
  - 代わりの指定を用意して使うもの：`lh` 単位、相対色構文（`rgb(from …)`）、`light-dark()`、`text-wrap: balance`
  - 使わないもの：`text-box-trim`、`interpolate-size`
- カスケードレイヤー（`@layer`）は、ブラウザでは使えるが、**WordPress の案件では使わない**
  （レイヤーの外にある WordPress・プラグインの CSS に、必ず負けるため）。

## 8. コメント

- 説明は `//` で書く（`/* */` は、コンパイル後の CSS に残る）。
- ファイル・ブロックのタイトルだけ `/* */` で書く（CSS を読む人が、場所を探せるように）。
- 借りたコードの出典・ライセンスは `/*! */` で書く。
- 「何をしているか」より「なぜそうしているか」を書く。

## 9. アクセシビリティ（SCSS で守ること）

- `outline` を消すだけの指定をしない。消すなら `:focus-visible` で、代わりの見た目を必ず用意する。
- 動きのある演出には `@media (prefers-reduced-motion: reduce)` を必ず添える。
- JS で開閉する要素の「閉じた状態」を、初期値にしない（JS が動かないとき、中身が隠れたままになる）。
  開いた状態を初期値にして、JS が付けるクラス（`is-enhanced`）があるときだけ、閉じられるようにする。
- 文字サイズは `rem` を基本にする（ブラウザの文字サイズの設定が効くように）。
- クリック・タップの対象は 24×24px 以上（推奨 44×44px）。

## 10. CMS のエディタで入力する本文

- 本文を出す枠には `c-entry` を付ける。【論点13】
- **枠の中だけは、タグ（`h2` `p` `ul` `table`）と、ブロックのクラス（`wp-block-〇〇`）に直接 CSS を当ててよい**
  （入力する人は、BEM のクラスを付けられないため）。枠の外では、タグに CSS を当てない。
- ブロックエディタで、ブロックに独自のクラスを足すときは、`ex-` で始める（`ex-has-border`）。【論点13】
- エディタの中の見た目を、公開ページとそろえる（エディタ用の CSS に、同じファイルを読み込む）。
  エディタ用の CSS には、リセットとベースを入れない（管理画面の見た目が崩れる）。

## 11. 既存の案件を直すとき

- **その案件の書き方に合わせる。** このルールと違っていても、書き直さない
  （1つのファイルに、新しい書き方と前の書き方が混ざるほうが、読みにくくなる）。
- 関数・mixin の名前と使い方は、その案件の定義を先に読む。**同じ `mq` という名前でも、案件によって向きが逆のことがある。**
- 新しく足す部品だけをこのルールで書くかどうかは、勝手に決めず、先に確認する。

## 12. オプション（使う案件だけ）

- **行間の余白の補正（`--leading-trim`、`g.flow-space()`、`g.trim-end`）**：Photoshop のカンプ（文字の見た目から余白を測る）の
  案件だけで使う。XD・Figma の案件では使わない。使う案件は、`CLAUDE.md` に書く。Flex / Grid の `gap` とは一緒に使わない。【論点9】
- **文字サイズの設定表（`lv1`〜`lv6` と、それを呼び出す mixin）**：見出しの大きさを、サイト全体でそろえる。
  設定表に無い大きさを、部品のファイルで勝手に増やさない（増やすときは、設定表に足す）。
