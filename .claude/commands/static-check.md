静的コーディングの成果物を確かめて、CMS の実装に進んでよいかを報告する。対象：$ARGUMENTS

**このコマンドでは、見つけた問題を勝手に直さない。** 直すかどうかは、報告のあとで人が決める。
`.claude/rules/static.md` を先に読む。

## 確かめること

1. **表示できる**
   - Eleventy の案件：`npm run build` が通る。
   - PHP の案件：開発環境の URL（`/_html/`）で、全ページがエラー無く開く。
2. **成果物がそろっている**（`static.md` §2）
   - デザインのある全ページ、ページの一覧、本文の見本ページ、状態の見本、引き継ぎメモ。
   - 無いものは、「無い」と挙げる（勝手に作らない）。
3. **デザインと合っている**（ページごと）
   - デザインと同じ幅（PC・スマホ）で、スクリーンショットを撮る。
   - デザインのデータ（XD の案件は `design/` の画像、Figma の案件はフレームのスクリーンショット）と並べて、違いを挙げる。
     場所・どう違うか・おおよその大きさ（例：「見出しの下の余白が、デザインより 8px 広い」）を書く。
   - その間の幅（タブレットなど）で、崩れが無いことを確かめる。
4. **中身が変わっても崩れない**（`static.md` §4）
   - 長い文章、0件、画像なし、などの見本があり、崩れていない。
5. **本文の見本ページ**（`static.md` §3）
   - 使う部品がそろっている。CMS が実際に出力する HTML で書かれている（自分で考えた HTML になっていない）。
6. **CMS に組み込みやすい形になっている**（`static.md` §5）
   - 共通パーツが1か所にまとまっている。`CMS:` のコメントがある。パス・ページごとの値が、変数にまとまっている。
7. **自動のチェック**：`/pre-delivery` の内容（アクセシビリティ、HTML、CSS・JS、残っているもの）。

## 報告の形

最初に、判定を1行で書く。

- **進んでよい**：デザインとのずれが無い（または、理由があって残すものだけ）。
- **直してから進む**：ずれ・足りないものがある。
- **判断できない**：確かめられなかったものがある（理由を書く）。

そのあとに、表を出す。

| ページ | デザインとの一致（PC / スマホ） | 状態の見本 | 違い・足りないもの |
|---|---|---|---|

最後に、次を並べる。

- **人が確かめること**：実機での表示、キーボードでの操作、動きの印象、文言の正しさ。
- **CMS を実装する人に伝えること**：デザインに無かったので補ったもの、確かめられなかったもの。
- 確かめたこと・確かめていないこと。

## 守ること

- スクリーンショットを撮れなかった・デザインのデータを読めなかったときは、「合っている」と書かない。「未確認」と書く。
- 「だいたい合っている」と、まとめない。違いは、小さくても挙げる（残すかどうかは、人が決める）。
