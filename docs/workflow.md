# 作業の流れと担当（AIと人）

デザインから公開までを、誰が（どのチームが）・何を使って進めるかの決まりです。

- **AI** ＝ Claude Code が下書き・実行する
- **人** ＝ 人が決める・確かめる・実行する

## 全体の流れ

| # | 工程 | 担当のチーム | AI | 人 |
|---|---|---|---|---|
| 1 | デザイン制作 | 制作 | ― | デザインを作る。`design-handoff.md` の決まりでデータを整える |
| 1.5 | CMS とテーマの種類を決める | システム・制作 | 選択肢の比較を出す | **コーディングの前に** 決める（WordPress はクラシック / ブロック / ハイブリッド。下の表） |
| 2 | デザインの受け渡し | 制作 | 足りない情報・矛盾を質問として洗い出す | 質問に答える。データを直す |
| 3 | 静的コーディング | 制作 | `/design-to-code` で共通パーツ → 各ページの順に作る。本文の見本ページ・状態の見本も作る | 1ページごとにデザインと見比べる。動きの調整を指示する |
| 4 | 静的 HTML の確認 | 制作 | `/static-check` で、デザインとの一致・足りないものを報告する | 実機・キーボードで確認する。**CMS の実装に進んでよいかを決める** |
| 5 | CMSの設計 | システム | テンプレート・投稿タイプ・入力項目（ブロックテーマは部品ごとの作り方）の案を表にする | 「更新箇所の一覧」（下）を決める。プラグインを決める |
| 6 | CMSの実装 | システム | `/static-to-wp` でテーマを作る。開発環境で表示して確かめる | 管理画面の設定をする。入力のしやすさを確かめる |
| 7 | 納品前の確認 | システム → 制作 | `/pre-delivery` とセキュリティ監査を行う | 報告を読み、直す所を決める。顧客に確認してもらう |
| 8 | 本番への反映 | システム | 手順書・確認項目を作る | **サーバー・DBの操作はすべて人が行う** |
| 9 | 保守 | 制作 | 原因を調べる。修正のコードを作る。開発環境で確かめる | 本番に反映する。顧客に連絡する |

## なぜ、静的 HTML を先に作って確かめるのか

デザインとのずれには、「コーディングのずれ」と「CMS の仕様とのずれ」の2種類があります。

- **静的 HTML の段階で、デザインと合っていることを確かめておく**と、CMS に組み込んだあとでずれたとき、
  原因を「CMS の側」に絞り込めます。作業が2つのチームに分かれているので、この切り分けが大事です。
- **CMS の仕様とのずれは、組み込みの段階で見つかると、デザインからやり直しになります。** そこで、
  静的 HTML の中で、CMS が実際に出力する HTML（本文の見本ページ）と、中身が変わったときの状態（長い文章・0件など）を
  再現して、先に見つけます。
- さらに手前で防ぐために、**デザインの前に、CMS の制約をデザイナーに伝えます**
  （本文はエディタで入力する、件数や文字数は変わる、など）。
- 静的 HTML は、組み込んだあとの「正解の見本」として残し、デザインの変更があったら、先に静的 HTML を直します。

くわしい決まりは `.claude/rules/static.md` にあります。ブロックテーマの案件は、標準のブロックが HTML を決めるので、
静的 HTML をそのまま使えない所が出ます。その場合は、CMS の仕様に合わせてデザインすることが中心になります。

## WordPress のテーマの種類の選び方

ブロックテーマは、標準のブロックが WordPress の決めた HTML を出力するため、静的コーディングの HTML をそのまま使えない所が出ます。
**コーディングを始める前に決めてください。**

| 種類 | 顧客が変えられる範囲 | デザインの再現 | 作る手間 | 向いている案件 |
|---|---|---|---|---|
| クラシック | 文章・画像・決めた入力項目 | 高い（静的 HTML をそのまま使える） | 小 | デザインを固定したいコーポレートサイト |
| ハイブリッド（クラシック＋`theme.json`） | 上に加えて、記事の本文をブロックで自由に組める | 高い（骨組みは固定） | 小〜中 | 骨組みは固定、記事だけ自由にしたい |
| ブロック | ページの構成・ヘッダー・フッターまで | 部品による（独自ブロックにすれば保てる） | 大 | 顧客が自分でページを作り変えたい |

迷ったら、ハイブリッドから始めるのが安全です（あとからブロックテーマへ寄せていける）。

## Movable Type の案件

テンプレートは管理画面に貼って再構築するまで動かないため、AI が自分で動作を確かめられません。
AI はテンプレートの下書きまで、**貼り付け・再構築・表示の確認は人が行います**（`.claude/rules/movabletype.md`）。

## 人が必ず行うこと（AIに任せない）

| すること | 理由 |
|---|---|
| デザインとの見た目の最終確認 | AIは数値どおりに組めても、数pxのずれや印象の違いに気づきにくい |
| スマホ実機・キーボード・スクリーンリーダーでの確認 | 自動チェックで見つかるのは、問題の一部だけ |
| 「どこを顧客が更新するか」を決める | 顧客との打ち合わせの内容で決まる |
| プラグインを決める、本体・プラグインを更新する | 相性と保守の責任が伴う |
| 本番サーバー・本番DBの操作 | 取り返しがつかない。個人情報がある |
| 顧客とのやり取り、納品の判断 | 責任を持てるのは人だけ |

## AIに頼むときのこつ

- **1回の依頼は1ページ（または1つのパーツ）まで。** まとめて頼むと、確認しきれない量が一度に出てくる。
- **共通パーツ（ヘッダー・フッター・ボタン・見出し）を先に作る。** あとのページがそれを使い回すので、見た目がそろう。
- **出てきたコードは、その場で表示して確かめる。** 直してほしい所は「どこが・どう違うか」を具体的に伝える
  （例：「PC幅で、見出しと本文の間がデザインより10px広い」）。
- **同じ注意を2回したら、ルールに書く。** `CLAUDE.md` か `.claude/rules/` に書き足すと、次から言わなくて済む。

## 更新箇所の一覧（案件ごとに記入する）

CMSの実装（工程5）の前に、システムチームと制作チームで決めて記入する。
`/static-to-wp` は、この表をもとにテンプレートを作る。

| ページ | 場所 | 顧客が更新するか | 入力の方法（本文エディタ / カスタムフィールド / メニュー など） | 備考 |
|---|---|---|---|---|
| 【例：トップ】 | 【メインビジュアルの画像と文言】 | 【する】 | 【カスタムフィールド】 | 【最大5枚】 |
| 【例：お知らせ】 | 【記事の本文】 | 【する】 | 【本文エディタ】 | |
| 【例：フッター】 | 【住所・電話番号】 | 【しない】 | 【テンプレートに直接書く】 | |

## 引き渡しのチェックリスト

### 制作 → システム（静的コーディングの納品）

- [ ] `/static-check` の判定が「進んでよい」になっている
- [ ] `/pre-delivery` の結果に「要対応」が残っていない（残すものは理由を書いた）
- [ ] 全ページをデザインと見比べた（PC・スマホ）
- [ ] キーボードだけで、メニュー・フォーム・スライダーを操作できた
- [ ] 本文の見本ページがあり、CMS が実際に出力する HTML で書かれている（記事の本文エリアがある案件）
- [ ] 長い文章・0件・画像なしの見本がある
- [ ] 引き継ぎメモを書いた（CMS 側で変えてよい所・変えてほしくない所）

### システム → 制作（CMS実装の完了）

- [ ] 静的HTMLと同じ見た目・同じ動きになっている
- [ ] 「更新箇所の一覧」の項目を、すべて管理画面から変えられる
- [ ] セキュリティ監査の結果に、重大な指摘が残っていない
- [ ] フォームの送信を開発環境（MailHog）で確かめた
- [ ] 管理画面で人が行った設定を、メモに残した
